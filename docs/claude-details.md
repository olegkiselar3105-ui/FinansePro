# FinansePro — подробности (полная прежняя версия CLAUDE.md, до сжатия 2026-11-07). Читать нужный раздел при работе над темой.

## Что за проект

Учёт доходов и расходов в Telegram: Mini App (веб-приложение внутри Telegram) + бот.
Пользователь пишет или наговаривает боту «кофе 300», приложение превращает это в запись.

## Поток данных

1. Пользователь → бот в Telegram. Telegram шлёт обновление на воркер `POST /webhook`
   (проверяется заголовок `X-Telegram-Bot-Api-Secret-Token` = `WEBHOOK_SECRET`).
2. Воркер: голос → Groq Whisper → текст. Текст кладётся в очередь пользователя:
   D1 (`env.DB`, мгновенно) или, если D1 не привязана, KV (`env.FIN`/`env.INBOX`, с задержкой).
   Бот отвечает «в очереди». Есть дневной лимит на пользователя (`DAILY_LIMIT`).
3. Открытый Mini App опрашивает `GET /api/pending` (адрес воркера — `BOT_URL` в `index.html`).
   Авторизация: приложение передаёт `initData` Telegram, воркер проверяет подпись токеном бота.
4. Приложение само разбирает фразу и сохраняет запись: Telegram CloudStorage + localStorage.
   Воркер записи не разбирает и не хранит финансовые данные — только очередь сырых фраз (до 30 дней).
5. Приложение шлёт `POST /api/ack` (какие id приняты, какие не разобраны, что сделано) →
   бот меняет своё сообщение на «✅ Записано: …».

Следствие: логика разбора фраз и все данные — в `index.html`; воркер — транспорт и голос.

## Секреты и переменные

Хранятся только в Cloudflare: Workers → finansepro → Settings → Variables and Secrets.

- Секреты: `BOT_TOKEN`, `GROQ_KEY`, `WEBHOOK_SECRET`.
- Переменные: `ALLOWED_IDS` (пусто = бот открыт для всех), `DAILY_LIMIT` (по умолчанию 60), `APP_URL`.
- Привязки: KV `FIN` (или `INBOX`), D1 `DB`.

Репозиторий публичный. Токены, ключи, секреты и личные id пользователей в код и коммиты не писать.
id привязок KV/D1 в `worker/wrangler.toml` допустимы: это не секреты, без них не работает автодеплой.
Для локального запуска — `worker/.dev.vars` (в `.gitignore`), образец — `worker/.dev.vars.example`.
`BOT_URL` в `index.html` — публичный адрес воркера, это не секрет.

## Как обновлять

Приложение:
- правки в `index.html` / `sw.js` → коммит в `main` → GitHub Pages обновится сам за 1–2 минуты;
- при каждой правке `index.html` поднимать `IB_VER` (формат `v`+число) — по нему приложение
  замечает новую версию и перезапускается; `APP_VER` — видимая версия, менять по смыслу;
- `sw.js` берёт версию кэша из `IB_VER`, отдельно её не трогать.

Воркер (автоматически, Cloudflare Workers Builds):
- слияние в `main` → Builds собирает `worker/` и выполняет `wrangler deploy`;
- код в панели вручную не править — следующий деплой его перезапишет;
- привязки (KV, D1) объявлять в `wrangler.toml`: привязки, которых нет в файле, при деплое удаляются;
- секреты и переменные живут в панели; `keep_vars = true` не убирать, иначе деплой сотрёт переменные.

Если меняется формат API между приложением и воркером (`/api/pending`, `/api/ack`) — изменения
должны быть обратно совместимы: приложение и воркер обновляются в разное время.

## Правила работы со мной

- Отвечай на русском, прямо, без похвалы.
- **Формат ответов (требование пользователя, действует всегда):** структурировано, как конспект. Заголовки с номерами шагов; в каждом шаге — что делать, где нажать, что должно получиться; **жирным** — ключевые слова, названия кнопок и результат шага; списки и короткие абзацы, готовые тексты и команды — в отдельных блоках; в конце — «что дальше». Должно быть понятно с первого взгляда, что делаю я и что делает пользователь. Объяснять простыми словами. Это важнее прежнего «не перегружать форматированием».
- Во время работы — коротко и понятно описывай, что делаешь сейчас и зачем (1–2 простые фразы на шаг, без длинных разборов).
- В конце — кратко: что сделано и что добавлено; если были проблемы — какие и из-за чего. Без разборов, пояснений и инструкций по проверке, пока не спрошу.
- После правок присылать в чат файлом `index.html` (превью вне Telegram); копия кода — в Cloudflare (`tools/codebackup.sh save`). Страница изменений при необходимости: `python3 tools/diffpage.py gh-main HEAD "vNNN" <scratchpad>/changes.html`.
- Не соглашайся автоматически: если идея слабая или противоречивая — скажи прямо и предложи лучше.
- Перед изменениями давай план и жди подтверждения, если изменение затрагивает логику, данные или API.
- Никогда не добавляй токены и ключи в код — репозиторий публичный.
- После важного решения добавляй запись в `DECISIONS.md` (формат: дата — решение — причина).
- `index.html` большой (~650 КБ): читай нужные участки поиском (grep по имени функции/строке), а не целиком.

## Окно «Что нового»

- Выпуск — `const WN=[...]` в `index.html`. В списке **только один, последний выпуск**: новый заменяет старый (старый удалять), `{id:'ГГГГ-ММ-ДД', items:[['эмодзи','Заголовок','Короткое описание'], ...]}`; `id` должен быть новым (по нему окно показывается один раз). Требование пользователя (с v204).
- Показывается каждому пользователю один раз (отметка `cfg.wnSeen` синхронизируется через облако Telegram), новым — после обучения.
- Анимация окна «Что нового» (v205): обёртка `.wnx`, у пунктов `--i` (очередь появления), `--n` — число пунктов; при закрытии содержимое тает.
- Новый выпуск — только когда пользователь скажет; текст — простым языком, для обычных людей, коротко (1–2 строки на пункт). Эмодзи с текстом внутри (📅 показывает «July») не брать.

## Категории

- `CAT2` — прежний набор (у всех, кто пользовался приложением до v165, у них `cfg.catV===2`), `CAT3` — общий набор для новых. Набор выбирает `catSet()`; не менять это так, чтобы существующие пользователи получили другой набор.
- Ключевых слов у категорий нет. Порядок фразы (v235): заметка, сумма, категория — слова сразу после суммы, если с них начинается название категории (или первое слово названия), это категория («кофе 300 кафе»); также работает «… категория X»; иначе — память `learn`, иначе «Прочее». Названная категория запоминается для заметки при записи (`commit`, пометка `lrn`).

## Связь операций с долгами и целями (v180)

- Операция, созданная из долга или цели, хранит `t.lk={k:'d'|'g', id, e, p}`; запись истории — `e.t` (id операции). Возвраты — `d.log` (меняют `paid`), выдачи/займы — `d.ol` (меняют `amount`), взносы — `g.log` (меняют `saved`).
- Источник правды — операции: `lkSync()` в `save()` подгоняет долги и цели под список (удаление, сумма, дата, смена категории, «Отмена», слияние с облаком). Не менять суммы долгов/целей в обход этого, если запись связана: менять операцию, а `save()` сделает остальное.
- Правки в «Планах»: `lkDebtEdit`/`lkGoalEdit`; удаление долга/цели убирает их операции (`lkDrop`). Старые записи связываются один раз (`lkMigrate`, отметка `cfg.lkM`) — только однозначные совпадения.
- Лимиты и бюджет считаются из операций каждый раз — связь им не нужна.
- v198 (двусторонняя связь, шаг 1): у каждой записи журнала (`d.log`, `d.ol`, `g.log`) есть `id` (старым выдан без связывания); удалённая запись помечается в `cfg.del` по своему id — как операция (все удаления записей: `jDel`, `lkSync`, `lkShrink`). Запись → операция: `jDel(e)` (удаляет и связанную операцию, возвращает данные для `jUndo`), `jEdit(e,сумма,дата)` (меняет и операцию). Долг и цель получают метку правки `u` (`snapDG`, как `snapTx` у операций); слияние с облаком — `dgMerge`: версия посвежее + записи журнала по id, помеченные удалёнными выбрасываются, добавленные на другом устройстве добавляются со своим влиянием на сумму. Дата начала долга — `d.created`, редактируется в окне долга (`dStart(d)` — у старых без неё дата первой записи); первая выдача и её операция переносятся на эту дату. Связь закрепляется при создании записи: переключатель «Записывать…» влияет только на новые записи; старые записи автоматически больше не связываются (разовое связывание v180 `lkMigrate` уже прошло).
- v199–v200: нажатие на плитку долга/цели открывает историю (`openHist`, `histHtml`, строки `dRows`/`gRows` — записи журнала + «начальные» суммы без записи; правка записи — `openJEdit`/`jSaveCur` в окне `#bq`). Цвет строки — по движению денег: из кошелька красным «−», в кошелёк зелёным «+» (поле `f` строки: `o`/`i`). Кнопка «Показать в операциях» (только если есть связанные операции) — фильтр списка `flk={k,id}`, плашка `#chip` с «К долгам/К целям». Удаление связанной операции (`delEd`, `delTx`, кнопка в строке): в плашке «также из долга/цели: …» (`lkWhere`), «Отмена» возвращает и долг, созданный этой операцией (`lkKeep`). Плитка долга (v200): «осталось X» справа, тип долга и срок отдельной строкой, дата начала и последний возврат ниже; прогноз «При таком темпе…» на плитке долга убран (`debtFc` не вызывается).

## Валюты (переделка по шагам, с v195)

Цель: операция хранит свою сумму, валюту и курс на момент записи; основная валюта (`cfg.cur`) — только способ показа. Решено: новые данные пишутся в новое место в облаке (старая версия на другом устройстве не может их испортить), связанная с долгом/целью операция записывается в валюте долга/цели.
- Шаг 1 (v195, сделан): `cfg.rh` — история курсов `{EUR:[[дата,курс,база,источник]]}` («1 EUR = курс базы»; m — вручную, a — авто, c — подтверждён при смене валюты), одна запись в день на валюту и базу, до 400; пишет `rhAdd`, сливает `rhMerge` (облако, импорт). Пока на показ не влияет. Копия перед сменой валюты — `finapp.cbk` (до 2, `cbkSave`/`cbkRestore`, кнопка «Вернуть как было» в окне валют). Импорт JSON из файла в другой валюте пересчитывает суммы по курсу (у операций сохраняются `oc`/`oa`), без курса — не импортирует.
- v196–v197: строка суммы в окне операции — `[EUR ▾] 5   MDL 100` (валюта, сумма; посередине основная валюта простой подписью и её сумма; у обычной операции `[MDL ▾] 28`), под ней курс (`edCurHtml`/`edCurBind`/`edCurLine`). Сумма в валюте → основная по курсу операции; основная → сумма в валюте по тому же курсу (курс не меняется). Значок валюты — `select` внутри `label` (меню v147), список: основная + добавленные (`edCurs`). Смена валюты: число остаётся, курс — текущий для новой валюты; основная — операция становится обычной; нет курса — поле ввода курса, при сохранении он становится ручным курсом валюты. Окно не перерисовывается. Черновики после «+» — пока по-старому.
- Большая переделка (шаги ниже) отложена по решению пользователя. Если вернёмся: единый способ получить сумму для показа вместо прямого `.amount` (159 мест) → миграция и новое место в облаке → запись новых операций со своей валютой → смена валюты без перезаписи → показ по курсу на дату → бюджет/лимиты/цели/долги/повторы в своей валюте → экспорт/импорт. Каждый шаг — с планом и подтверждением.

## Полезные места в index.html

- `IB_VER`, `APP_VER` — в самом начале файла (5–6-я строка, отдельный `<script>` после CSP). `IB_VER` должен оставаться в первых ~4 КБ: проверка новой версии читает только начало страницы и обрывает загрузку. Не переносить его ниже.
- `BOT_URL` — искать `const BOT_URL`.
- `ibCall`, `ibBase` — обращения к воркеру.
- `CloudStorage` — синхронизация данных через облако Telegram.
- Суммы форматировать только через `fmtN`/`fmt` (готовые форматировщики `_nf0`/`_nf2`), не создавать `Intl.NumberFormat` в циклах (v202). Список месяца строить целиком за один раз: досборка частями после анимации (v202) на iPhone дёргала свайп месяцев — каждая дописанная часть перерисовывала большой слой списка; отменено в v203. Смена месяца (`swapAnim`, v205) — системной анимацией `el.animate` (Web Animations), не кадрами из скрипта (`pxAnim`): на iPhone она не замирает, пока строится новый месяц. Дни списка всегда с `content-visibility:auto` (класс `cv`, v205; высота-заготовка `contain-intrinsic-size` у каждого дня) — невидимые дни не раскладываются; это ускоряет смену месяца и открытие/закрытие окон (переключение прокрутки `wlk` раскладывало весь список).
- Прокрутка страниц: у каждой страницы и раздела своя (`PGY`, ключ `pgKey`). Любая смена страницы или раздела — `pgSave()` до, `pgApply()` после `render()` (так делают `slideTo`, `slideSub` и нажатие на разделы).
- Фокус в поля окон ставит сама iOS по касанию. Не перехватывать касание полей и не переводить фокус между полями из программы: iOS тогда не меняет вид клавиатуры (цифры/буквы) и рисует курсор и выделение не там (так было в v189–v191, отменено в v192). От прокрутки «к полю» защищает блокировка документа: пока открыто окно, у корня нет прокрутки — страницу прокручивает `body` (`html.wlk`, `wlk()` в `lockBg`). Поэтому прокрутку страницы читать и задавать только через `pgY()`/`pgTo()`, а не `window.scrollY`/`scrollTo` (`window.scrollY` при открытом окне — 0; его же читает Telegram, подменять нельзя). Касание по самому тексту неактивного поля скачет (iOS ставит курсор в точку касания), касание подписи строки — нет; поэтому у каждого текстового поля в окнах есть `label` (строка `label.ef`, обёртки `.eaw`, `.rvf`, `label.fld`/`.ncr`/`.tgf`/`.cpw`), а неактивное поле пропускает касание на неё (`pointer-events:none` до `:focus`, блок v193). Новое поле в окне — только внутри `label`. Программный фокус (autoF и т. п.) — `focus({preventScroll:true})`. Пока окно едет за клавиатурой, у него класс `kbmv`: курсор прозрачный, выделение текста ждёт остановки (v190).
